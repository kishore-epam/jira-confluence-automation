# Specification Review and Clarifications

## Review scope

Reviewed [constitution.md](./constitution.md), [specification.md](./specification.md), and the Module 08 source specification at [project_spec.md](../work/module03-task/project_spec.md). Each material gap, contradiction, or unclear requirement is resolved below as either **Answered in spec** or **Out of scope**. The decisions marked answered are incorporated into `specification.md`; no implementation-critical question remains open for the single-user local prototype.

## Gap review

| ID | Gap, contradiction, or unclear requirement | Resolution | Disposition |
|---|---|---|---|
| C-01 | The constitution's React/Node/PostgreSQL stack did not explain how it coexists with Module 08's Python report generator. | React/Vite is the local UI, Express is the application API, PostgreSQL is the database, and the Python 3.12 worker performs scheduled report generation through authenticated loopback API endpoints. The worker does not connect directly to PostgreSQL. | **Answered in spec** — Overview; API Endpoints |
| C-02 | The prototype's deployment topology and supported user count were unspecified. | The prototype is local to one dedicated, non-shared Windows account. UI, API, worker callbacks, and database bind to loopback; Docker Compose runs PostgreSQL only. Remote, multi-user, and production use are prohibited. | **Answered in spec** — Prototype boundary |
| C-03 | Browser/API authentication was unclear for a single local operator, and worker authentication was unspecified. | The local Windows account is trusted for browser use; browser requests are constrained by loopback, exact origin, and Host validation. The worker uses a setup-generated 256-bit-or-greater token from Windows Credential Manager, sent as a bearer token. | **Answered in spec** — Prototype boundary; API data rules |
| C-04 | Secret storage, database credential delivery, and the previously suggested `.env` approach conflicted with the constitution's secret-handling rule. | Windows Credential Manager is assumed to be organization-approved for this prototype. The startup wrapper supplies database credentials to Compose at runtime; no `.env`, committed defaults, shell history, logs, or source files contain credentials. Docker access is restricted to the dedicated project-manager account and machine administrators. | **Answered in spec** — Overview; Prototype boundary; Assumptions |
| C-05 | It was unclear whether integrations, direct connectors, or controlled files were the supported source path. | The prototype accepts controlled UTF-8 CSV only. Jira, Git, Confluence, capacity, and PM-template schemas, scope allowlists, metadata, freshness rules, and validation are defined. | **Answered in spec** — Prototype CSV contracts |
| C-05b | The constitution mentioned XLSX although the prototype's source-import contract is CSV-only. | The constitution now states that XLSX parsing requires a separately approved specification change. | **Out of scope** — Prototype boundary; Open Decisions; Constitution, Security and least privilege |
| C-06 | Module 08 names a PM spreadsheet template, while the application also has PM narrative fields, creating two potential sources of truth. | The supported PM-template CSV populates an unsaved form draft. The project manager reviews and saves it; the saved, versioned application update is canonical. Native Excel/XLSX parsing is not included. | **Answered in spec** — User Story 7; Prototype CSV contracts; API Endpoints |
| C-07 | Required versus optional sources and the behavior of partial reports were unclear. | PM narrative and current Jira issues, sprint, and sprint-scope datasets are mandatory. Missing or stale optional datasets produce a partial report with the affected measures unavailable and warnings; invalid or missing required inputs fail the run. | **Answered in spec** — Prototype CSV contracts; FR-029; API/UI requirements |
| C-08 | Reporting-window boundaries, daylight-saving behavior, and retry anchoring were ambiguous. | The interval is the half-open period from Monday 9:00 a.m. to the next Monday 9:00 a.m. in `America/New_York`, seven local calendar days (possibly 167 or 169 elapsed hours). UTC instants are persisted, and retries reuse the original scheduled anchor. | **Answered in spec** — Metric and period definitions; SC-001; SC-012 |
| C-09 | Source timestamps and coverage requirements could permit stale or incomplete data to be used silently. | Uploaders provide extraction time and coverage metadata. Inputs are current only within the seven-calendar-day freshness threshold and must cover the required interval; sprint-scope history must cover the sprint. Uploader-supplied metadata is explicitly an assertion, not cryptographic source verification. | **Answered in spec** — Prototype CSV contracts; FR-031; API data rules |
| C-10 | The five-day issue-aging rule did not define business days, holidays, or exact threshold behavior. | Business days are weekdays Monday–Friday with no holiday exclusions. Age counts weekdays in `(last_updated_local_date, report_end_local_date]`; the threshold is reached at five days. Continuous in-progress age is greater than ten calendar days and requires transition history. | **Answered in spec** — Metric and period definitions; FR-035 |
| C-11 | Sprint committed, completed, remaining, and scope-change calculations lacked precise membership semantics. | Scope CSV rows represent continuous membership intervals; re-adds are separate non-overlapping rows. Baseline points use membership at sprint start; completed and remaining points use distinct issues and their membership intervals; additions/removals are reported separately. Missing history or estimates yields partial/unavailable metrics. | **Answered in spec** — Metric and period definitions; Prototype CSV contracts |
| C-12 | Milestone health could rely on unspecified PM-entered status, despite no structured PM status field. | Milestones are complete when mapped to `done`, overdue when incomplete with a due date before report end, and otherwise on track. Missing status/date makes health unavailable. The prototype uses PM milestone changes as narrative only, not as a separate health override. | **Answered in spec** — Metric and period definitions; Prototype CSV contracts |
| C-13 | Weekly planned capacity and rolling-interval worklog actuals use different periods, and person-level data handling was underspecified. | Actual worklogs cover the exact rolling interval. Planned capacity is the full Monday–Sunday plan starting on the interval's local Monday and is shown separately without proration. Person-level capacity rows are aggregated in memory and immediately discarded. | **Answered in spec** — Metric and period definitions; FR-025; CapacityAggregate |
| C-14 | Client-facing eligibility of Jira issue titles, milestones, and Confluence summaries was not operationally defined. | Jira issue/milestone and Confluence rows carry `client_shareable`; the local project manager attests that flags were reviewed. Only true rows may appear by name/reference; unshareable blockers are represented only as aggregate counts. | **Answered in spec** — Prototype CSV contracts; API Endpoints; Standard Report Layout |
| C-15 | The source specification's broad slide-count range conflicted with the requested concrete report layout. | The prototype produces exactly six slides in a fixed order. Missing or partial measures are labeled on those slides; no additional caveat slide is added. | **Answered in spec** — FR-012; FR-036; Standard Report Layout |
| C-16 | Forecasts were required conditionally, but no approved calculation method, evidence threshold, or confidence method was supplied. | Forecast values and calculations are disabled in this prototype and shown unavailable; users cannot configure a threshold to enable them. | **Out of scope** — Prototype boundary; UI Screens; SC-010; Open Decisions |
| C-17 | Deployment/release data and other unapproved source content had no identified source. | Deployment/release measures remain optional and unavailable until an approved source exists. Automated Confluence summarization is also excluded; supplied summaries may be used only for eligible pages. | **Out of scope** — Prototype boundary; FR-011; Open Decisions |
| C-18 | Report cadence, PM deadline, late-update handling, and missed-run recovery were unclear. | The worker runs Monday at 9:00 a.m. Eastern; PM input is due at 8:30 a.m. A late update saved before 9:00 may be used and is labeled late; an update after the trigger is ineligible for that run. A missed trigger is not replayed. | **Answered in spec** — FR-021; FR-043–044; Open Decisions |
| C-19 | Manual generation and recovery from missing required data were not distinguished from automatic retries. | The prototype has no manual-generation endpoint. Missed runs and runs that fail because required PM/Jira inputs are unavailable are not recoverable; the next attempt is the next scheduled week. | **Out of scope** — Prototype boundary; API data rules; Open Decisions |
| C-19b | The retry limit, retry inputs, and behavior after a late worker completion were unclear. | Transient API failures receive at most three retries at 1, 5, and 15 minutes within 30 minutes, using the same period, PM revision, source IDs, and settings version. Validation failures are terminal; an expired or duplicate completion cannot replace a newer artifact. | **Answered in spec** — FR-039; API Endpoints |
| C-20 | The meaning of “latest,” artifact preservation, and retention conflicted for failed or partial runs. | Every successful or partial run creates an immutable dated artifact and atomically updates `latest.pptx` and the project pointer. Failed runs never replace artifacts. Dated reports and the associated latest copy are removed at the one-year deadline. | **Answered in spec** — FR-013–014; ReportArtifact; Operational retention; SC-006–007 |
| C-21 | Human review and report distribution requirements were not connected to application behavior. | The project manager can record an append-only approval or changes-requested decision with an optional note. Review does not trigger a retry or distribution; there is no email, publish, or automatic-send action. | **Answered in spec** — User Story 5; FR-015; FR-034; UI Screens |
| C-22 | Retention periods for source files, capacity data, report records, logs, and reports were not consistently specified. | Accepted non-capacity files are deleted within seven days; rejected temporary uploads and capacity CSVs are deleted immediately. Capacity aggregates and report records are retained one year; logs 90 days; dated report retention is one year. | **Answered in spec** — FR-032; FR-038; Operational retention |
| C-23 | The data model could be mistaken for a finalized physical database design. | The entities are logical requirements only. SQL types, indexes, migrations, backup/recovery, high availability, production performance, and disaster recovery are not defined for this local prototype. | **Out of scope** — Data Model; Open Decisions |
| C-24 | The supported browser and operating-system baseline were unspecified. | The prototype supports current stable Microsoft Edge on Windows at desktop width. | **Answered in spec** — UI Screens |
| C-24b | Mobile layout, cross-browser certification, and formal accessibility conformance were unspecified. | These are not prototype acceptance requirements. Controls must nevertheless remain keyboard-operable and use semantic labels. | **Out of scope** — Open Decisions |
| C-25 | Branding, corporate PowerPoint template, and detailed visual styling were not specified. | The report uses a neutral stakeholder-oriented presentation and the six required content sections. A branded corporate template, custom visual identity, and pixel-level design specification are deferred. | **Out of scope** — User Story 4; Standard Report Layout |
| C-26 | Precise technology versions and local container baseline were not consistently recorded. | The specification pins React 18.3.1, Vite 7.3.7, Node.js 24.22.1, Express 5.3.0, PostgreSQL 15, Docker Desktop 4.97.0, Compose CLI v5.6.1, and Python 3.12. | **Answered in spec** — Overview; FR-023 |

## Remaining future-scope decisions

The remaining decisions apply only if the product moves beyond this prototype: enterprise identity and authorization; remote/network deployment; source-system connectors and their identities; forecast methodology; production database migrations, backup/recovery, and operational support; and any change to the stated privacy or retention rules. These are explicitly blocked pending a separately approved specification change.
